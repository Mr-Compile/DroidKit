# J18 — Shizuku Journey Plan (2026-10-19)

Docs: playbook `20`, checklist Journey 18, v2 `23_CAPABILITY_ADVANCED_ACCESS_V2`,
v2 `22_PERMISSION_APPOPS_LAB_V2` (elevated parts).

## Audit — what already exists

- `privilege:shizuku` — full `ShizukuProvider` (dep `dev.rikka.shizuku:api:13.1.5`):
  binder liveness, permission check/request via `OnRequestPermissionResultListener`,
  `runShell` through `Shizuku.newProcess` (reflection — documented approach).
- `privilege:root` — full `RootProvider` (su detect + `su -c` + grant round-trip).
- `core:privileges` — `ElevatedAction` allow-list (validated, injection-proof),
  `ElevatedExecutor`, `ProviderSetup`, `ElevatedOps` router (SHIZUKU→ROOT→ADB).
- `Set<CapabilityProvider>` bound in `AppModule`; status surfaces on Settings.

## Gaps to close this journey

1. **DI**: `ElevatedOps` injects `Set<ElevatedExecutor>` + `Set<ProviderSetup>`
   — neither set is bound. Providers already implement the interfaces; add
   the two set provisions in `AppModule`.
2. **Setup UX**: provider rows in Settings are read-only. Add a per-provider
   dialog (status + instructions) and a Grant button calling
   `ElevatedOps.requestGrant(kind)` when `NeedsSetup`.
3. **AppOps feature** (`feature:appops`): replace `FeatureStubScreen` with a
   real AppOps Lab —
   - package picker over `pm list packages` via `ElevatedAction.ListPackages`
     (elevated path sees the full set, not the manifest-restricted view),
   - `appops get <pkg>` parsed into op rows,
   - mode change via `ElevatedAction.SetAppOp` behind an explicit
     consequence dialog (SafetyLevel.SYSTEM_CHANGE already declared).
   - No-provider state = honest "elevated provider required" card with a
     link hint to Settings → Advanced access.
4. **Read-only proof**: AppOps screen header shows `id` output from
   `ElevatedAction.WhoAmI` once, as the elevated-access proof of life.
5. **Tests**: `AppOpsParserTest` (op/mode rows, malformed lines) +
   `ElevatedActionTest` (command strings, injection rejection).

## Non-goals

- Package disable/clear/uninstall stay ADB-gated (J19) — declared
  `Capability.ADB_SHELL`; unchanged.
- No raw shell input UI — actions remain allow-listed only.
- Device verification of real Shizuku grant flow is owner/hardware-bound;
  code-complete items only tick after compile + unit tests.
